# 可选桌面探索失败后的恢复边界

这是 2026-11-06 的只读设计记录，下面的结构化目标范围尚未实现。当前两项纯文件恢复检查保留为预期失败，没有通过放宽电脑结果核验来消除失败。

## 已确认的问题

一次尚未派发输入的桌面尝试，仍可能留下任务级 GUI 义务和工具失败；之后即使文件已经读回、原始文件要求与独立裁判通过，任务仍为 `needs_user`。只读桌面观察失败也可能阻止其它已完成结果被正常结算。

不能直接清除这些义务。初始 `GoalContract.from_task` 只推导文件要求，不代表已完整列出自然语言的所有要求。“打开应用并创建文件”可能只有文件要求被推导出来；受控强负例中，即使裁判乐观通过、文件真实存在，没有打开应用仍必须不能完成。`requires_gui_evidence` 仅能增加核验要求，未匹配不能证明任务不需要 GUI。

## 可复用的基础

`GoalContract` 已有要求标识、文件实证及结果核验；`GuardedGoalTimeline` 已有修订、摘要及可信纠正来源。效果台账、桥接累计未知状态和先前输入的核验责任仍分别保留，不应按工具名称整体清除。一次可选探索的结束不能代替原始目标完成。

## 后续最小方向

1. 只有可信的结构化文件入口，才能声明已完整枚举的文件目标范围；普通自由文本继续视为开放范围。声明绑定任务、会话、目标修订及要求摘要，模型、网页、工具返回均不能将范围改成完整。
2. 每条失败义务绑定本次调用身份、目标修订、对应要求或可选探索身份。仅确认这一次可选探索未派发、没有累计未知效果或先前 GUI 输入责任时，才可结束该探索义务；原始失败事件保留。
3. 如用户明确修改本次目标，可复用可信纠正时间线改变目标要求；旧纠正重放和模型伪造不生效。目标改变也不能清除尚未确认的实际输入效果。

这两种路径都无需增加模型请求，但第一种不覆盖普通自然语言任务，第二种需要用户的明确新意图。让现有裁判顺便声称“桌面步骤不需要”只能提供建议，不能签发完整范围。当前未增加新的用户模式、关键词分派或确认流程，也未启用这些设计。
