# DeepSeek Harness 迁移记录

本次将 Agent 核心替换为官方 Harness SDK，而非只移植计划工具或修改名称。Windows 源码版本 1.1.0，Android 1.20.0；新的分发包须另行通过构建与验收。

## 已验证的边界

- 官方 SDK 通过本地模拟服务完成写文件、交付、退出进程和新进程恢复同一会话；文件字节由测试独立检查。
- 同一路径检查原生工具开关、用户问题、下一轮补充指令、取消、子进程密钥隔离、图片恢复与禁止旧图再次上传、缺失会话拒绝替换、DeepSeek 思考参数。
- Python 宿主经真实 Node / SDK 完成文件交付和会话恢复，另检查任务归属、停止期间派发、实际关闭回执、下载副本和手机公开活动。
- 桌面与手机的确认正文上限统一为 16,000 字；超出显示能力的请求拒绝执行，不通过截断后的说明取得批准。

本地模拟服务不消耗用户 API，也不证明真实模型会正确选择工具。SDK 新任务启动在本机约 4–5 秒，暂未改为常驻进程池。

## 本轮发现与修正

第一次完整 SDK 测试的补充指令用例错误地期待修改已经发出的模型请求，已改为检查下一轮；此前失败保留。既有进程生命周期测试使用 Python 可执行文件缺失来阻断启动，迁移后改为 Node 缺失；这组测试还发现并补上启动前取消检查和注册失败后的精确子进程关闭。

首次真实服务验证在 QA 中继启动时失败，未调用模型，原因是抽离测试网络代码时漏带 DNS 模块，已补齐。该次配置文件哈希有变化，不能宣称配置稳定；后续两次相同读取方式未变化。接着真实服务两次返回 HTTP 422，尚未执行工具。原因是 SDK 在本地中转地址下无法按 URL 识别 DeepSeek，发出了 `developer` 消息和错误参数；现按已识别的模型协议明确使用 `system`、`max_tokens`，不发 `store`。

修复后两次独立文件任务各用 5 次模型请求。均读取两份新建输入，得到合计 46、种类 2，写入 JSON、读回并 `present`；独立检查输入文件未变、输出 JSON 和下载副本长度 / SHA256 一致，进程收尾确认。第一次功能通过但配置文件哈希被并行运行的桌宠改动，整体配置稳定项未通过；第二次 15.88 秒，API 配置及整份配置文件哈希均未变化，完整通过。此前失败没有覆盖，累计账本为 **23 / 100**（本轮 12 次，含 2 次 422）。这些是自有文件夹任务，不是复杂电脑操作成功率。

另修正升级兼容：电脑本地同步 schema 从 11 升至 12，重建公开活动白名单触发器；手机增加 DSH 标签，避免新操作被静默过滤。Android 1.20.0 最终 322 项 JVM / Robolectric 检查与 Release Lint 通过，四份原签名 APK 通过完整性与对齐检查；未进行实体手机验收。

更换为 Node 24.22.3 并修正 SDK 初始化失败收尾后，真实服务又完成一次同类独立文件任务：14.83 秒、5 次模型请求，输入保留、输出字节与下载副本校验、API 配置一致和资源关闭均通过。该次整份设置文件哈希发生变化，因此不宣称全部个人设置完全未变；QA 未写入设置，原运行中的程序仍在使用配置。累计账本为 **28 / 100**，本次 DSH 迁移使用 17 次，其中包含前述两次 422。报告保留每一轮，不覆盖早期失败。

## 来源与保留项

Windows CUA 原生组件通过 104 项官方协议检查；随后实际窗口测试发现上游响应已可读、后台写操作尚未退出时会误判 `NATIVE_BUSY` 并断开连接。已修复这一竞态并保留原始源码、差异及双方哈希。修复后的 250 次无延时连续请求、自有 WinForms 窗口发现、中文与 emoji 输入、点击、504×347 截图、过期观察拒绝和进程收尾均通过。官方 SDK → `cua` → 原生 helper → 最终回复的链路另通过本地模拟模型验证。

进一步的整栈检查发现两个发布阻塞，首轮 Windows 候选因此没有交付：其一，已发布 CUA 要求数字窗口 ID，新版 Windows 原生模块使用字符串，单独的 helper 测试和 SDK `listApps` 都没有覆盖这个交界。现用每连接随机安全整数映射原始字符串，64 位窗口值不经过浮点转换，旧连接引用拒绝复用。其二，Windows broker 位于宿主 Job 之外，上游 SDK / Cordis 还可能吞掉清理错误，所以进程退出或 SDK shutdown 返回都不能单独证明输入已结束。现验证每条原生连接的关闭回执，按任务、会话和随机 nonce 签名绑定，宿主收到证明后才确认停止；缺失证明保留未确认状态和下一任务阻挡。远程任务另持久化外部清理标记，重启后不能只凭 Job 为空解除阻挡。

实际 SDK 自有窗口链路已验证：应用确认、窗口列表、UIA、中文与表情输入、截图进入模型，在鼠标处于按下状态时取消，收到关闭证明后按钮释放且没有后续输入。使用 7 次本地模拟模型请求，真实 API 调用为 0。缺少关闭回执、丢失签名、会话不匹配等反例单独检查。这里的签名用于绑定本次宿主协议，不代表已隔离同一 Windows 用户权限下的恶意本机代码。

后续 40 项整套的一次原生停止用例未捕获按住状态，失败保留。增强诊断后的两次复测确认测试窗口未取得前台，均在发送全局输入前拒绝继续；这不能倒推首次失败的唯一原因。其间完整链路也有一次通过，前台由测试窗口预置，不能声称 SDK 自行激活任意应用成功。当前桌面被使用时已停止全部前台输入复测，独立安装验收改为明确标记的非交互范围。

39 项非前台复测又发现收尾阶段一次 `DSH_STOP_UNCONFIRMED`。诊断确认 SDK 已答复 shutdown，但随后触发 Windows libuv `UV_HANDLE_CLOSING` 断言，子进程退出码为 3221226505。已移除重复 shutdown，改为观察官方 SDK 唯一一次关闭的真实回执；连续 10 次专项复测通过，但随后 40 项非前台整套仍有 1 项出现同一退出崩溃，不能将重复关闭认定为唯一原因。该结果与前台占用无关，两个旧候选均未交付，安装器和 ZIP 压缩已中止。

独立核对发现 Node 24.15.0 存在高度吻合的退出竞态：停止延迟任务调度器后仍可能向已关闭的 libuv handle 发消息。官方 [PR #61999](https://github.com/nodejs/node/pull/61999) 已修复，首次进入 [24.20.0](https://nodejs.org/en/blog/release/v24.20.0)。当前改用经官方校验的随包 Node 24.22.3，重新执行整套和独立安装检查；不修改系统 Node，不忽略异常退出，也不放宽停止证明。

新运行时下，47 项非前台专项检查通过、没有跳过，原退出崩溃任务连续 10 次通过。独立审查另修正启动前失败的收尾：版本、配置或目录等错误发生在 SDK 尚未构造时，明确报告没有启动操作，避免宿主永久保持忙碌；真实进程一旦启动仍须通过全部停止证明。上述检查未操作用户当前窗口，不替代新包的原生键鼠验收。

随后补齐官方 SDK 初始化失败会更换内部 client 的分支：在原 client 启动前观察关闭回执，始终核对真正启动过的进程，不把尚未启动的替代 client 当作原任务。真实 SDK 的初始化失败、自动关闭与重建路径通过，电脑工具开启但未发送输入。最终冻结代码 **48 项非前台检查通过、0 跳过**，同代码的退出任务再连续 10 次通过；宿主与运行时 **188 项**加实际宿主→SDK **4 项**通过，共 192 项不同 Python 用例。早期 47／39 项及重复执行不累加为独立用例数。

早期原生停止证明和窗口协议修正后的 Node 适配回归曾有 **39 项通过、0 跳过**，后续失败如上单独保留，不能用早期通过掩盖最终状态。宿主与兼容回归 176 项通过，另有 4 项真实 SDK 集成检查；其中真实 React / WebChannel / Qt 备用界面 17 项通过：16,000 个表情的问题完整显示，8,000 个表情的回答完整发送，超限保留草稿并提示。电脑操作实测仅限自有窗口，不能等同于浏览器登录、支付、复杂办公或任意游戏操作均已验证。

当前明确限制：普通聊天里已有的旧图片不会自动重发到新 DSH 会话；从普通聊天切换到 Agent 后需要重新选择要分析的那张图片。DSH 会话自身已接收的图片可在原生会话恢复后继续引用。原生 SDK 单任务启动仍约 4–5 秒；定时任务和运行时插件安装在本嵌入方式中未开启。

官方发布的核心 / SDK 与 Windows CUA 最新源码虽使用相同版本号，接口并非完全一致；来源、兼容补丁和许可证分开记录，见[第三方记录](../third_party/deepseek_harness/README.md)。

历史 Agent 源码的批量删除被自动审批拒绝且未提供具体原因，因此保留历史文件；当前运行与打包明确排除它们。没有通过换工具再次执行删除。旧版失败、隔离限制和已发布 1.0.2 的验收记录继续保留，不当作新 DSH 的验证结果。
